完成判定的六种状态 —— 为什么不能合并

业界最普遍的 bug 是把「这一轮说完了」当成「活干完了」。Claude Code 的官方文档自己承认 task status 会滞后并阻塞依赖任务。所以这里刻意做成六个互不相同的徽标，任何两个合并都会丢失信息。

徽标契约（design §6 的可视化）

运行中 L1 · TurnStart / hook turn_completed 之前 实心点 + 呼吸动画。有活动才出现。 空闲 L1 · TurnEnd{Completed} / hook turn_completed 灰点、无动画。它说完了，但没声明干完。 待批准 L1 · RequestApproval / hook approval_requested 琥珀。人必须动手。进待批队列，不冒泡进队长对话。 完成 L2 · task_update(state=done) 绿。唯一权威：任务板 state == done。 未声明 L1 有、L2 无 琥珀虚线圈 + 空心点。结果可用但必须标黄 —— 没人认领这次「完成」。 可能等待输入 L3 · 超阈值静默，且该 CLI 无 input_requested 紫。文案不许写「正在工作」。诚实优先于好看。 已退出 L4 · SessionDone / 进程退出 红。触发租约回收，任务退回待认领。

三条不变量（要写成测试）

  • 空闲永不自动升级为完成。否则「它说完了」会被当成「它做完了」。
  • 完成的唯一权威是任务板，不是成员状态。成员可以 idle 而任务仍 in_progress。
  • 未声明只降级、不消失。标黄的结果仍可被队长使用，但使用者必须知道它没被认领。

CLI 成员准入 —— 三档，不许假装统一

本期队长与成员都是 PTY 里的 CLI agent。但「能跑在 PTY 里」远不等于「能当队员」：一个成员至少要能被观测到「这一轮结束了」，否则它完成了也没人知道。所以准入必须分档，且每一档在 UI 上都要看得见。

队长的等待为什么是「物理阻塞」

本期队长也是 CLI，所以 team_wait 发生在一个 MCP 工具调用内部：工具不返回 → 队长这一回合就不会结束。它在物理上没有「边等边自己去干活」的机会。

这正是 Claude Code 那个官方缺陷（lead 自己动手不等队友，"修法"是改 prompt）的克星：它把等待做成了提示词行为，我们把它做成了工具调用语义。

结果取证（L1b）

  • turn_completed 到达后，按 (agent_id, native_session_id) 回读该 CLI 的会话文件，取最后一轮 assistant 文本 —— 不解析屏幕。
  • 复用 conversation/ 已有 10 个 adapter（已归一化 + 已按字节预算分页）。
  • 无 MCP 的成员拿不到 task_update，所以结果永远显示「未声明」 —— 这是诚实，不是缺陷。

sentinel：零集成的结果通道（你提的那条）

成员把结果打印到自己的 stdout，Neeko 从 PTY 字节流里扫这一行 —— 不需要 hook、不需要 MCP：

NEEKO_RESULT 7f3a91 {"executionId":"e-42","task_id":"t1","status":"completed","summary":"…"}

接受条件四条（缺一即静默丢弃）：① 前缀 + nonce 精确匹配 ② JSON 可解析且 status 合法 ③ task_id 存在且 owner == 本成员、state ∈ {in_progress, awaiting_approval} ④ executionId 未消费过。

第 ③ 条是关键：回显出来的模板里 task_id 通常是占位符或旧值，会被权威状态校验直接杀掉。扫描器本身流式有界（carry ≤8KB / 单行 ≤2KB），绝不无界累积 —— 那个 pump 的历史事故是 WebView 8 分钟涨到 5.2GB，红线 4 就是那次写的。

审批策略（每成员，`approval_policy`）

值行为用在哪
Queue请求进待批队列，人来批默认
Interactive在成员自己的 PTY 里交互用户就坐在那个 pane 前
Bypass用该 CLI 的旁路开关启动只读调研 / 沙箱内；UI 必须有非隐蔽警示

旁路开关是 per-CLI 数据（落插件数据，红线 15），四家写法各不相同：codex --dangerously-bypass-approvals-and-sandbox · gemini --skip-trust --approval-mode yolo · grok --always-approve · claude --dangerously-skip-permissions --permission-mode bypassPermissions。团队代码里禁止按 CLI 名分支。

为什么成员 transcript 默认不进前端

成员各自在自己的 PTY 里由 xterm 渲染，走既有终端通道 —— 团队事件只带状态与摘要（≤4KB）。点开成员时走 conversation 分页（已有 ≤1.5MB/页 预算）。这是红线 4 的直接要求。

一次完整流程（点顶栏「推进演示 →」走一遍）

这条链路要验证的是：队长从不轮询、审批不冒泡、完成必须被声明。

1
建队 + 派活
队长调 team_spawn ×3 和 task_create ×3。只有队长能 create；成员只能 claim 或 propose。
2
成员原子认领 + 起租约
task_claim 是原子的：两人抢同一任务只有一个成功。租约 1800s 起算，任务进 in_progress。
3
队长阻塞等待
team_wait(until=declared) 在后端阻塞。队长没有机会「自己去干活」 —— 这正是 Claude Code 那个官方缺陷的根因。
4
成员撞到审批门
backend 要写 src/server/auth/** → 进待批队列，任务转 awaiting_approval。队长看到的是队友「待批准」，而不是对话里多一条审批卡。
5
人批准 → 成员继续
后端把状态推回 Running。审批不经过任何 agent 转交 —— 成员不能代替人批准，也不能把被拒的动作转交同伴绕过。
6
首个成员轮次结束但未声明
frontend 的 Stop hook 到达 → 成员 Idle。但没调 task_update(done) → 落 完成⚠ 未声明。队长拿得到结果，但知道它没被认领。
7
声明完成 → team_wait 返回
成员调 task_update(state=done, summary, artifacts) → 任务 done。全部目标达 declared → 队长被唤醒，拿到摘要。
8
失败路径：成员被杀 → 租约回收
进程退出 → Dead → 租约到期任务退回 pending（reclaim_count +1）。超过 3 次转 blocked，不再自动回收。这是防死锁的唯一机制。
