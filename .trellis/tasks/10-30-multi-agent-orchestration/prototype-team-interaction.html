② 审批收件箱 —— 多 agent 审批必须是「收件箱」，不能是散落弹窗

调研对照（research/05 §B1/B2）：单 agent 行内审批；多 agent 汇聚成收件箱 + attention。 Claude Code teams 的反例：teammate 权限请求上浮到 lead 会话行内、无队列无批量，实测每会话点几十次批准， 且 "always allow" 规则不随 teammate 继承（issue #26479）。Neeko 已有 Queue 策略语义（R0b），本原型给它可操作的面。

卡片上的三个动作

  • 批准 —— 向成员 PTY 写入其 CLI 的确认键序列（各 CLI 的写法落 HookTarget/插件数据，团队域不按名分支）；成员回 Running，任务回 in_progress。
  • 拒绝 —— 写入拒绝键序列；成员收到 CLI 自己的拒绝处理，可附一句话说明（排队下一条消息）。
  • 总是允许… —— 把本次决策沉淀为规则（bash(npm run deploy *) · 作用域=本成员），并执行本次批准。 ⚠ 规则的作用域与继承是裁决 B 的一部分 —— Claude Code teams 的教训：规则不继承 = 摩擦重现。

为什么批准动作是「写入 PTY」

成员是 CLI（本期唯一路径）：审批框渲染在它自己的 PTY 里，Neeko 不解析它。 hook 只上报「有审批请求」；批准/拒绝 = 向该 PTY 写对应键序列。因此收件箱卡片上 没有「批准前改命令」（那是 Chat 成员/未来阶段的梯级，见视图③）——这也是本原型在卡片上 只给「看 PTY」而不给编辑的原因。

③ 插话与接管 —— 排队是默认，打断是显式，接管是渐进

调研对照（research/05 §B3/B4/B5）：Claude Code（Enter 排队 / Esc 打断 / Up 取回）、 Codex（Tab 排队）、Warp（waiting tab attention）。共同约定：输入永远不丢，打断要用专门的键。

⚠ 裁决 A：主面隐喻 —— 本原型按「成员 + 审批为主面、任务板退为页签」绘制

备选维持板为主（与旧原型/AC11 一致，改动最小），行动入口塞进现有布局。

影响：若采纳推荐项，prototype-agent-team.html 视图①与 AC11「四视图逐条落地」需同步修订。

⚠ 裁决 B：UI 代行队长职权的边界 —— 本原型按「UI 可操作审批；建/改/派任务仍走队长」绘制

推荐UI 审批（本来是 3.2 计划内）+ 重新派发按钮（显式回收，落审计「用户代队长」）；任务创建仍只有队长 task_create（R1.7 不动）。
更保守UI 仅审批+观察，重新派发也让队长做 —— 权限矩阵零改动，但「换人重做」要靠提示词。

影响：推荐项需 authorize.rs 加 actor 概念（user-on-behalf-of-lead）与审计标注；「总是允许」规则的作用域（本成员/全队）也在本裁决内。

角色预设 —— 人设（persona）与授权（MemberRole）必须分开

现状：`MemberRole` 只有 Lead | Worker，它是授权矩阵的维度（design §3.2：谁能调哪些工具）； worker preamble 全员一份（identity::preamble，C14 机制）。而「研究员 / 实现者 / 评审员」是另一个维度 —— persona：preamble 文本 + CLI 偏好 + 审批策略 + 缺省工作区的数据包。 不能往 `MemberRole` 里加变体 —— persona 若能改变授权，spawn 就成了提权后门；正确落点是一份新数据， 在 spawn 时被消费、且只能落在 spawn 时本来就允许定的参数上（审批档位、工作区、CLI 选择）。
