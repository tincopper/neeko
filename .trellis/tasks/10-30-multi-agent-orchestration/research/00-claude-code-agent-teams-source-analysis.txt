第1章 概述
1.1 什么是 Agent Teams
Agent Teams 是 Claude Code 内置的多代理协作框架，允许多个 AI Agent 以团队形式协同工作。当单一 Agent 面对复杂任务力有不逮时，Agent Teams 能将工作分解为可并行的子任务，分派给多个独立的 Claude Code 实例并行执行。
在这个框架中，每个团队成员是一个独立的 Claude Code 实例。它们各自拥有独立的对话上下文、工具权限和执行状态，通过以下机制协调工作：
消息传递系统：基于文件邮箱（Mailbox)的异步通信，Agent 之间通过写入 JSON 文件交换信息

共享任务列表:所有团队成员共享一个基于文件系统的 TaskList，用于追踪和分配工作

统一领导管理:由 team-lead 角色统一管理团队生命周期、任务分配和成员调度

1.2 快速使用指南
理解源码之前，先看 Agent Teams 怎么用。用户不需要直接调用底层 API，而是通过自然语言告诉 Claude Code 要做什么，Claude Code 会自动调用 TeamCreate、SendMessage、Agent 等工具完成团队编排。
1.2.1 最简单的用法：一句话创建团队
在 Claude Code 对话中输入：
用团队来帮我重构这个项目的前端和后端
Claude Code 会自动执行以下步骤：
调用 TeamCreate 创建团队

通过 Agent 工具生成多个队友（frontend-worker、backend-worker）

使用 TaskCreate 创建任务并分配给各队友

通过 SendMessage 协调队友工作

完成后调用 TeamDelete 清理团队

1.3 核心设计理念
Agent Teams 的架构建立在五个核心设计理念之上。这些理念贯穿于整个代码库，理解它们是把握系统全貌的关键。
1.3.1 文件即协调
Agent Teams 选择文件系统作为跨进程协调的核心机制。团队配置(config.json)、成员邮箱(inboxes/{name}.json)、任务列表(tasks/{team-name}/)均为磁盘上的 JSON 文件。这一设计带来三个关键优势:
进程无关性:无论是同进程的 In-Process Agent，还是通过 tmux/iTerm2 独立启动的 Agent,都使用同一套文件协议通信

天然持久化:Agent 崩溃后消息不会丢失,重启后可以继续处理未读消息

调试友好:开发者可以直接查看文件内容理解系统状态

邮箱系统使用文件锁(lockfile)来防止并发写入冲突:
// src/utils/teammateMailbox.ts:36-41
const LOCK_OPTIONS = {
 retries: {
 retries: 10,
 minTimeout: 5,
 maxTimeout: 100,
 },
}
每次写入邮箱时,先获取文件锁,读取最新消息列表,追加新消息,再写回磁盘,最后释放锁。这一"读-改-写"原子操作确保了多个 Agent 并发写入时数据不丢失.
1.3.2 双模式执行
Agent Teams 支持两种执行模式:Pane-Based(终端面板模式) 和 In-Process(同进程模式).
Pane-Based 模式通过 tmux 或 iTerm2 的原生面板功能,为每个 Agent 创建独立的终端窗口.每个 Agent 是一个完整的操作系统进程,拥有自己的 Node.js 运行时。
In-Process 模式则在同一个 Node.js 进程内运行所有 Agent.通过 Node.js 的 AsyncLocalStorage API 实现上下文隔离,使多个 Agent 的身份信息(agentId、teamName、color 等)互不干扰.这种方式资源消耗更低,且 Agent 之间可以共享 API 客户端和 MCP 连接. 后端选择由 registry.ts 中的 isInProcessEnabled() 自动决定,逻辑如下:
// src/utils/swarm/backends/registry.ts:351-389
exportfunction isInProcessEnabled(): boolean {
// 非交互式会话强制使用进程内模式
if (getIsNonInteractiveSession()) {
 returntrue
 }

const mode = getTeammateMode()

let enabled: boolean
if (mode === 'in-process') {
 enabled = true
 } elseif (mode === 'tmux') {
 enabled = false
 } else {
 // 'auto' 模式:如果在 tmux 或 iTerm2 中,使用面板后端;否则使用进程内模式
 const insideTmux = isInsideTmuxSync()
 const inITerm2 = isInITerm2()
 enabled = !insideTmux && !inITerm2
 }
return enabled
}
1.3.3 统一抽象
TeammateExecutor 接口屏蔽了不同执行后端的差异,使上层代码无需关心 Agent 是运行在 tmux 面板中还是同一进程内:
// src/utils/swarm/backends/types.ts:279-300
export type TeammateExecutor = {
 readonly type: BackendType
 isAvailable(): Promise<boolean>
 spawn(config: TeammateSpawnConfig): Promise<TeammateSpawnResult>
 sendMessage(agentId: string, message: TeammateMessage): Promise<void>
 terminate(agentId: string, reason?: string): Promise<boolean>
 kill(agentId: string): Promise<boolean>
 isActive(agentId: string): Promise<boolean>
}
这一接口有两个实现:
InProcessBackend(src/utils/swarm/backends/InProcessBackend.ts):通过 AsyncLocalStorage 管理生命周期,使用 AbortController 终止

PaneBackendExecutor(src/utils/swarm/backends/PaneBackendExecutor.ts):适配器模式,将 PaneBackend(tmux/iTerm2)包装为 TeammateExecutor

通过 registry.ts 中的 getTeammateExecutor() 方法,调用者可以透明地获取适合当前环境的执行器.
1.3.4 身份隔离
对于同进程内的多个 Agent,Node.js 的全局状态(如环境变量、模块级变量)天然是共享的.Agent Teams 使用 AsyncLocalStorage 为每个 Agent 提供隔离的身份上下文:
// src/utils/teammateContext.ts:22-41
export type TeammateContext = {
 agentId: string // 完整 Agent ID,如 "researcher@my-team"
 agentName: string // 显示名称,如 "researcher"
 teamName: string // 所属团队名
 color?: string // UI 颜色标识
 planModeRequired: boolean // 是否需要计划审批
 parentSessionId: string // 领导者的会话 ID
 isInProcess: true // 类型判别标志

}

const teammateContextStorage = new AsyncLocalStorage<TeammateContext>()
身份解析遵循三级优先级:
AsyncLocalStorage(进程内 Agent) -- 最高优先级

dynamicTeamContext(运行时加入的 Agent)

环境变量(tmux/iTerm2 Agent,通过 CLI 参数传递)

// src/utils/teammate.ts:88-92

 const inProcessCtx = getTeammateContext()
 if (inProcessCtx) return inProcessCtx.agentId
 return dynamicTeamContext?.agentId
}

工具层(TeamCreate/SendMessage/TeamDelete) 是用户和 AI 交互的入口.这三个工具被注册为 Claude Code 的内置工具,AI 模型可以在对话中直接调用它们.工具层不直接执行 Agent,而是委托给执行层.
执行层(Backends) 负责实际运行 Agent.通过 TeammateExecutor 接口提供统一的 spawn/sendMessage/terminate/kill/isActive 操作.执行层会自动检测运行环境并选择最合适的后端.
协调层(Mailbox/TaskList/TeammateContext) 负责团队间通信、任务分配和身份隔离.所有协调机制都基于文件系统,确保进程无关性.

2.2.2 SendMessageTool -- 消息传递
SendMessageTool 是团队通信的核心工具.它支持五种操作:
普通消息(string):写入收件人邮箱

广播消息(to: "*"):写入所有非发送者的邮箱

关机请求(shutdown_request):请求 Agent 终止

关机响应(shutdown_response):接受或拒绝关机

计划审批(plan_approval_response):批准或驳回 Agent 的实施计划

}

3.1 邮箱架构
Agent Teams 使用基于文件系统的邮箱（Mailbox）作为跨 Agent 通信的核心基础设施。每个团队成员拥有独立的收件箱文件，路径格式为 ~/.claude/teams/{team-name}/inboxes/{agent-name}.json。
这一设计选择有三个关键考量：
跨进程兼容：无论是同进程运行的 In-Process Agent，还是通过 tmux/iTerm2 独立启动的进程级 Agent，都使用同一套文件协议

崩溃恢复：Agent 异常终止后，已写入邮箱的消息不会丢失，重启后可以继续处理未读消息

调试透明：开发者可以直接查看 JSON 文件内容，理解系统当前状态

邮箱文件存储的是一个 TeammateMessage 数组：

// src/utils/teammateMailbox.ts:134-192
exportasyncfunction writeToMailbox(
 recipientName: string,
 message: Omit<TeammateMessage, 'read'>,
 teamName?: string,
): Promise<void> {
await ensureInboxDir(teamName)
const inboxPath = getInboxPath(recipientName, teamName)
const lockFilePath = `${inboxPath}.lock`

// 原子创建文件（wx flag 在文件已存在时抛出 EEXIST）
try {
 await writeFile(inboxPath, '[]', { encoding: 'utf-8', flag: 'wx' })
 } catch (error) {
 const code = getErrnoCode(error)
 if (code !== 'EEXIST') {
 logError(error)
 return
 }
 }

let release: (() => Promise<void>) | undefined
try {
 release = awaitlockfile.lock(inboxPath, {
 lockfilePath: lockFilePath,
 ...LOCK_OPTIONS, // retries: 10, minTimeout: 5ms, maxTimeout: 100ms
 })
 constmessages = awaitreadMailbox(recipientName, teamName)
 constnewMessage: TeammateMessage = { ...message, read: false }
 messages.push(newMessage)
 awaitwriteFile(inboxPath, jsonStringify(messages, null, 2), 'utf-8')
 } catch (error) {
 logError(error)
 } finally {
 if (release) awaitrelease()
 }
}
解读：这是经典的"读-改-写"并发控制模式。writeToMailbox 先用 wx flag 原子创建文件（文件已存在则静默跳过），然后获取文件锁。锁策略配置了 10 次重试、5-100ms 退避，确保多个 Agent 并发写入时不会永久阻塞。获取锁后重新读取最新消息列表，追加新消息再写回。

 .filter(m => m.name.toLowerCase() !== senderName.toLowerCase())
 .map(m => m.name)

4.3 In-Process 后端
In-Process 后端是三种后端中最特殊的一个。它让所有 Agent 运行在同一个 Node.js 进程内，通过 AsyncLocalStorage 实现上下文隔离。

解读：In-Process 模式的决策链有四层。非交互式会话（-p 模式）强制使用，因为没有终端 UI，tmux 面板没有意义。用户显式配置优先。如果运行环境中既没有 tmux 也没有 iTerm2，则自动降级为 In-Process。inProcessFallbackActive 标志确保一旦降级，后续 spawn 不会反复尝试不可用的 pane 后端。

5.1 Agent ID 体系
Agent ID 是整个身份系统的基石，格式为 {agentName}@{teamName}。这个设计有两个关键特性：
可解析：通过 parseAgentId() 可以从 ID 中提取 agentName 和 teamName

确定性：相同的 agentName + teamName 组合总是生成相同的 ID

// src/utils/agentId.ts
exportfunction formatAgentId(agentName: string, teamName: string): string {
return`${sanitizeAgentName(agentName)}@${sanitizeName(teamName)}`
}

exportfunction parseAgentId(agentId: string): { agentName: string; teamName: string } | null {
const parts = agentId.split('@')
if (parts.length !== 2) returnnull
return { agentName: parts[0]!, teamName: parts[1]! }
}
Leader 的 Agent ID 固定为 team-lead@{teamName}。所有团队成员的 ID 都在创建时写入 config.json 的 members 数组。
sanitizeAgentName 的作用是消除歧义——将 @ 替换为 -，防止 agentName 中包含 @ 时与 ID 格式冲突：
// src/utils/swarm/teamHelpers.ts:109
export function sanitizeAgentName(name: string): string {
 return name.replace(/@/g, '-')

exportfunction isTeamLead(teamContext): boolean {

const myAgentId = getAgentId()

解读：isTeammate() 和 isTeamLead() 是两个互补的判断。isTeammate() 对 in-process Agent 直接返回 true（因为有 AsyncLocalStorage 上下文），对 tmux Agent 需要同时有 agentId 和 teamName（防止误判）。isTeamLead() 有一个向后兼容逻辑：如果当前实例没有设置 agentId 但有 teamContext，就认为是创建团队的原始会话（Leader）。
5.2.1 为什么 Leader 不设置 Agent ID
TeamCreateTool 的代码注释揭示了一个精心设计的不设置：
// src/tools/TeamCreateTool/TeamCreateTool.ts:224-228
// Note: We intentionally don't set CLAUDE_CODE_AGENT_ID for the team lead because:
// 1. The lead is not a "teammate" - isTeammate() should return false for them
// 2. Their ID is deterministic (team-lead@teamName) and can be derived when needed
// 3. Setting it would cause isTeammate() to return true, breaking inbox polling
如果 Leader 设置了 Agent ID，isTeammate() 就会返回 true，导致系统把 Leader 当作普通队友处理——启动收件箱轮询器（inbox poller）、发送空闲通知等，这些都是不期望的。
5.3 TeammateContext -- AsyncLocalStorage 隔离
TeammateContext 是 In-Process Agent 的身份容器，基于 Node.js 的 AsyncLocalStorage：
// src/utils/teammateContext.ts:22-41
exporttype TeammateContext = {
 agentId: string // 完整 ID: "researcher@my-team"
 agentName: string // 显示名: "researcher"
 teamName: string // 团队名
 color?: string // UI 颜色

 parentSessionId: string // Leader 的 session ID
 isInProcess: true // 类型判别标志
 abortController: AbortController // 生命周期管理
}

const teammateContextStorage = new AsyncLocalStorage<TeammateContext>()

exportfunction getTeammateContext(): TeammateContext | undefined {
return teammateContextStorage.getStore()
}

exportfunction runWithTeammateContext<T>(context: TeammateContext, fn: () => T): T {
return teammateContextStorage.run(context, fn)
}
解读：AsyncLocalStorage 的工作原理类似线程局部存储（Thread-Local Storage）。每个异步调用链都有独立的存储空间。当 runWithTeammateContext 执行时，它会为 fn 及其所有异步子调用建立一个独立的存储区域。之后，fn 内部任何位置的 getTeammateContext() 调用都会返回正确的 Agent 身份——即使多个 Agent 在同一个事件循环中并发运行。
AbortController 被包含在上下文中，用于生命周期管理。Leader 可以通过 task.abortController.abort() 终止 In-Process Agent 的所有异步操作。

关键设计点：Leader 在审批计划时，会将自己的权限模式传递给 Worker（除非 Leader 在 plan 模式中，则降级为 default）：
// src/tools/SendMessageTool/SendMessageTool.ts:434-476

 thrownewError('Only the team lead can approve plans.')
 }

const modeToInherit = leaderMode === 'plan' ? 'default' : leaderMode

 type: 'plan_approval_response',
 requestId, approved: true,

Worker 发送 PermissionRequestMessage 到 Leader 邮箱

Leader 收到后向用户展示请求

用户批准/拒绝

Leader 发送 PermissionResponseMessage 回 Worker

6.1 Task-Team 绑定
Agent Teams 的核心设计之一是 Team 和 TaskList 的 1:1 映射关系。创建团队时自动创建对应的任务目录：

解读：这个函数确保 Leader 和所有 Worker 都能找到同一个任务目录。Leader 通过 setLeaderTeamName 设置团队名，Worker 通过身份上下文（AsyncLocalStorage 或环境变量）获取团队名，两者最终都指向同一个 sanitizeName(teamName) 路径。

6.2.1 消息注入
当用户在 UI 中查看 Agent 的对话记录并输入消息时，通过 injectUserMessageToTeammate 注入：
// src/tasks/InProcessTeammateTask/InProcessTeammateTask.tsx:68-84

6.3.1 等待队友空闲
Leader 有时需要等待所有工作队友变为空闲后再执行操作（如关机）。waitForTeammatesToBecomeIdle 提供了这个能力：
// src/utils/teammate.ts:241-292
exportfunction waitForTeammatesToBecomeIdle(
 setAppState: (f: (prev: AppState) => AppState) => void,
 appState: AppState,
): Promise<void> {
const workingTaskIds: string[] = []
for (const [taskId, task] of Object.entries(appState.tasks)) {
 if (task.type === 'in_process_teammate' && task.status === 'running' && !task.isIdle) {
 workingTaskIds.push(taskId)
 }
 }
if (workingTaskIds.length === 0) returnPromise.resolve()

returnnewPromise<void>(resolve => {
 let remaining = workingTaskIds.length
 const onIdle = (): void => {
 remaining--
 if (remaining === 0) resolve()
 }
 setAppState(prev => {
 const newTasks = { ...prev.tasks }
 for (const taskId of workingTaskIds) {
 const task = newTasks[taskId]
 if (task && task.type === 'in_process_teammate') {
 if (task.isIdle) {
 onIdle() // 竞态处理：可能在我们检查后已经空闲了
 } else {
 newTasks[taskId] = {
 ...task,
 onIdleCallbacks: [...(task.onIdleCallbacks ?? []), onIdle],
 }
 }
 }
 }
 return { ...prev, tasks: newTasks }
 })
 })
}
解读：这个函数使用回调模式实现等待。它扫描所有运行中且非空闲的 In-Process Agent，为每个注册 onIdleCallback。当 Agent 变为空闲时，回调递减计数器，全部归零时 resolve Promise。注意竞态处理——如果 Agent 在我们扫描和注册回调之间变为空闲，直接调用 onIdle()。
6.4 生命周期管理
6.4.1 Terminate vs Kill
In-Process Agent 有两种终止方式，语义不同：
操作
方法
语义
实现
terminateterminate(agentId)优雅关机，发送协商请求

// InProcessBackend.ts:192-253
async terminate(agentId: string, reason?: string): Promise<boolean> {
const task = findTeammateTaskByAgentId(agentId, state.tasks)
if (task?.shutdownRequested) returntrue// 防止重复发送

 requestId: `shutdown-${agentId}-${Date.now()}`,
 from: 'team-lead', reason,
 })

}

async kill(agentId: string): Promise<boolean> {
const task = findTeammateTaskByAgentId(agentId, state.tasks)
const killed = killInProcessTeammate(task.id, this.context.setAppState) // abort()
return killed
}
解读：terminate 是协商式的——它发送关机请求，Agent 可以接受（退出）或拒绝（继续工作）。kill 是强制式的——直接调用 AbortController.abort()，取消所有异步操作。通常应该先 terminate，只在 Agent 无响应时才 kill。
6.4.2 Session Cleanup
创建团队时通过 registerTeamForSessionCleanup 注册到 Session 级别的清理集合。如果用户忘记调用 TeamDelete（如直接 Ctrl+C），cleanupSessionTeams 会在进程退出时执行：
// src/utils/swarm/teamHelpers.ts:576-590
