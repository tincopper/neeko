M1

诊断可视化闭环

R1 / AC1 · 已实现

Problems 面板从「孤儿组件」接入诊断数据流：诊断数据单写点 = lspStore，面板与编辑器波浪线共享同一事件源。

语言服务器 publishDiagnostics → Rust lsp-diagnostics-{projectPath} Tauri 事件 → lspStore diagnosticsByProject（单写点 · D3） → Problems 面板（本任务新增） │ lsp-client → CM squiggle（现状不动） 同一事件流两个消费面直接派生，不引入转发层 —— 避免「波浪线在、列表没有」的双表示病根（design D3）。

主场景：全窗口实景 Problems 面板展开 · 按文件分组 · severity 排序

空态与跨项目隔离 错误矩阵的两条边界

挂载点：三选一的实际落点 design §M1 判定标准 · 禁止新建第三种面板机制

M2

会话健康度可观测

R2 / AC2 · 未开始

目标：用户能自答「为什么没有提示」——LS 没起来 ≠ 没有该功能。四态：starting / running / failed / stopped。

Rust 会话生命周期钩子（spawn / handshake / exit） → 事件 lsp-health-{projectPath} 或复用 progress 前缀 → lspStore health 切片（幂等：同 phase 重放不闪烁） → status-bar item（语言图标 + phase + failed 重试入口） 白名单语义不动（D4）：这里只是新增一条 Rust→前端的推送事件，不涉及 server→client 请求。

四态在 status-bar 的呈现 现状 vs 增量，逐条标注

failed 展开态 AC2 要求「崩溃含重试入口」

阻塞 M1 收尾 / M2 开工

前四条来自 design.md 明确留给实现期的判断点；第 1、2 条是本次盘点新发现的落差。

1

M1 挂载点是否维持 (a) dock 固定底部面板？

已按 design §M1 判定标准落地为 (a)（与 Console / Debug 同构，零新增面板机制）。若你认为诊断该像 VS Code 一样常驻不占主区，或希望改为 (b) 折叠条，现在是改动成本最低的时点。

维持 (a)改 (b) 折叠条改 (c) status-bar 弹层
2

M2 是否收缩为「failed 原因 + 重试 + stopped 显式化」？

盘点显示 starting / running / error 圆点与 phase 文案仓库已有（LspStatusSection），重复实现会与既有 chip 竞争同一位置。建议 M2 只补两块：failed 的 error 详情与 Retry 入口；取消对 stopped 的过滤并给出明确终态。

收缩（推荐）按原计划全量做先只做 stopped
3

M3 灯泡入口落哪一处？

design 把编辑器内灯泡列为「可选增强，不做承诺」，主线是 Problems 行内。但诊断驱动的 quickfix 在业界心智是「光标所在行」，只在面板里点会弱一档。两条都做则需评估与 CM hover/tooltip 的竞态（design 风险表已列）。

仅 Problems 行内（最小风险）两处都做（体验完整）仅编辑器行号槽
4

Ask 的预览形态与 Never 的提示策略？

Ask 目前画的是居中弹层（带 Cancel / Skip import / Apply）。备选是补全面板内的行内 note（少一次焦点迁移，但预览多 edit 时空间紧张）。Never 的 toast 也可以静默去掉。

Ask 弹层 + Never 有 toastAsk 行内 noteNever 静默跳过
5

M0 真机验证谁来跑？

AC1 / AC3 的终验都需要真实 gopls（gopls version → 打开 Go 文件 → fmt. 补全 → 接受后 import 是否落块）。本原型是按「链路健康」画的；若实测发现 lsp-client 的 additionalTextEdits 落位有 bug，M3/M4 的原型前提要重估。
