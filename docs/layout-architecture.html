④ 状态源：谁管什么

状态源职责关键事实
dockStore 左右槽的全部布局事实：落位（谁是哪个槽 / 槽内序 / 有无图标）、槽展开与前台、视图宽度记忆 zustand persist v6；placements 是唯一真源，bar 与 zone 都是它的派生投影；merge 每次跑 sanitize（未知视图丢弃 / 非法槽位回默认 / order 归一化 / activeView 悬挂回落首个），左槽展开态重启强制 true
editorStore.editorLayout tab 的空间布局：中心组（left/right）+ pinned + docked 组（left/right 两个槽位 tab 宿主） 不持久化；docked 组是 tab「在哪个 surface」的唯一表示（不给 Tab 加 surface 字段）；移动只经 dockTab 原子迁移（单次 set 内先全域移除再插入 ⇒ 一条 tab 只在一个组，双 PTY 不可表示）；停靠的实例按当前 workspace 的 tabKey 投影，实例级停靠不持久化；形态判据也只读组：中心区 hasCenterTabs（left ∪ right ∪ pinned 且 id 仍在注册表，不数注册表）、zone 级 isZoneRenderable（展开 ∧ 前台有内容；宿主的内容事实 = countDockedTabs 的条数，由 app 经 useDockTabHostContent 注入）—— 两条共用同一个「存活 id」判定（空岛顶掉引导页 / 空宿主占位不会发生）
appViewStore 中心视图路由（normal/settings/library） 不持久化；appView:library 在 dockStore 里只占一个图标落位（host:none，不进 zone），两者经 toggleView 协同 —— 单一中心路由源
taskStore / debugStore 底部面板显隐（consolePanelOpen / panelOpen） 宿主不感知；面板高度各自 localStorage（neeko.task.consoleHeight 等）—— Step 3 时收编进 zone 体系
useZoneExpandCollapse zone 展开/收起 + 双 rAF resize 防「pin tab 后开面板 0 宽」历史竞态；挂起 rAF 随 effect 清理取消（快速展开→折叠不复发）

⑤ 依赖方向（编译期强制）

ui ← layout ← app ← features → shared layout/ 禁止 import features/* 与 app/*（ESLint import/no-restricted-paths）；app 通过 DockRegistryProvider 注入 registry、经 AppShell 注入 onMoveView / tabHostTabCounts（宿主里可渲染 tab 的条数 = tab 域事实；「非空」只在 isZoneRenderable 内部判 > 0）—— 骨架与业务只经 context / props 相遇

⑥ 扩展指南：加一个面板要改几处？

新增 Dock 面板（进左右区）

  • shared/dock/panelMeta.ts — 加一行 row(panelView('x'), { host, activation, defaultSlot, defaultOrder })
  • app/dock/registry.ts — 按同一个 ViewKey 加 title / icon / lazy 绑定
  • 需要 props 胶水时：app/dock/wrappers/ 每面板一文件
为什么这样registry 建表缺失绑定 / host≠none 缺 component 都会抛（buildDockPanelRegistry fail-fast）；layout 与 dockStore 完全不动，图标落位与 zone 渲染自动多一项。

新增底部固定面板

  • 只改 app/panels/registry.ts：加 { id, placement:'bottom', Component: lazy(...) }
  • 组合根 / AppShell / PanelHost 零改动
  • 显隐由面板自己的 store 驱动
护栏PanelHost 过滤逻辑有 mock registry 单测；registry.test 守护 id 唯一 / placement 合法 / Component 存在。

新增一个可停靠 tab 种类（种类级入口）

  • shared/dock/panelMeta.ts — 加一行 row(tabKindView('x'), { host:'none', activation:{kind:'openTab', tabKind:'x'}, defaultSlot:'right', defaultOrder, defaultOnBar:true })
  • app/dock/registry.ts — 加 title / icon（host:'none' ⇒ 不需要 component）
  • app/hooks/useDockBarOpenTab.ts — 补一条创建分支（OPENABLE_TAB_KINDS 加成员后 switch 穷尽性会报错）
为什么这样落地槽不写第三条策略：新 tab 落在图标当前所在的槽（placements 读，图标在哪栏就是答案），meta.defaultSlot 只作兜底。已有同类 tab 就只激活（含展开其宿主），所以“点两次开出两条”在构造上不发生。创建端口在 app 层（openTab 分支不直接写在 store 里：store 不持有 tab 空间）。

未来 Step 3：bottom 进布局

  • DockLayout 顶层加垂直嵌套 Group，bottom 槽入布局
  • DockSlot 联合加 'bottom'，并补一条 DOCK_SLOTS；placements/zones 的派生逻辑全部遍历该数组，不需要逐处加分支
  • zone 可见性判据（isZoneRenderable / zoneFrontView）与新槽无关；只需补内容事实端口：useDockTabHostContent 的 Record<DockSlot, number> 会因缺键编译报错（刻意用显式对象而不是遍历，新槽必须被看见）
  • dockStore 的槽状态按 Record<DockSlot, …> 扩展；复用 useZoneExpandCollapse
  • 触发条件：unified-task-hub 面板进底部，或底部需要拖拽/收起
已知风险react-resizable-panels 嵌套 Group 有历史 bug（pin tab → handle 失效）；实施时必须回归 pin-then-open 路径。sanitize 的「左槽强制展开」目前是特例，bottom 落地时需同时定义它的重启默认态。
